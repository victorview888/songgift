## 1. 项目目标与当前范围

SongGift 是面向海外用户的歌曲定制网站，主要流程为：填写故事 → 确认歌词 → 付款 → 生成歌曲 → 登录后查看、播放和下载。后续通过生日、婚礼、纪念日等英文场景页获取 SEO 流量。

后台用于经营与交付：查询订单、核对支付、处理生成异常、恢复歌曲保存，并逐步补齐用户、系统状态和运营统计。

当前后台仅完成管理员权限基础与入口，尚未实现七个后台页面的业务功能。

## 4. 已实现的管理员权限

### 4.1 页面与 API

- `/admin`：服务端验证管理员身份后，展示本人邮箱、Owner 身份和后台入口。当前只是权限验证入口，页面中“待接入”功能没有伪装成已完成业务。
- 未登录访问 `/admin`：转到 `/login?next=%2Fadmin`。
- 已登录普通用户访问 `/admin`：显示不包含管理员信息的访问受限/404 页面。
- `/api/admin/session`：每次请求都检查真实 Auth 身份与管理员成员记录。

API 状态约定：

| 状态 | 含义 |
| --- | --- |
| 200 | 已验证且当前是有效 Owner；只返回最小本人身份信息 |
| 401 | 未登录或邮箱未验证 |
| 403 | 无管理员资格、资格停用或角色不受支持 |
| 503 | 成员表、数据库或权限配置暂不可用；拒绝授权 |

成员配置不可用时，页面显示通用不可用提示，不展示管理员数据；页面本身不承诺返回 HTTP 503，后台 API 则返回 503。

### 4.2 授权边界

- 新增 `admin_members`，按已验证 Auth 用户 UUID 识别资格，首版只支持 `owner`。
- 只有 `active=true` 的 Owner 可以访问。
- 不信任邮箱白名单推断、用户可修改的 metadata、前端状态或请求中提交的角色。
- 每次受保护请求重新查询成员表；没有角色结果缓存，撤销后的下一次请求即被拒绝。
- 后台 API 统一使用 `adminRoute`，在执行任何业务查询前完成权限检查。
- 服务端后台页面使用 `getAdminPageAccess`；不要只在 layout 或前端检查权限。
- 保留现有同源写请求检查、JSON 限制、HttpOnly 会话及 private/no-store 响应。
- 特权数据库客户端只在服务端使用；普通客户端不能读取或修改管理员成员表。
- 原有客户订单 RLS 没有因新增后台而放开。
- 后台增加 noindex，robots.txt 排除 `/admin`；搜索控制不能替代鉴权。

### 4.3 登录衔接

将 `safeNext` 提取为不依赖服务端配置的共享模块，原服务端导出保持兼容。

已登录用户打开 `/login?next=/admin` 时，可通过“Continue to admin”返回后台。非法站外跳转、后台 API 地址及认证回调地址仍会被过滤。

### 4.4 数据库迁移与 Owner 工具

- `supabase/migrations/20261105_admin_permissions.sql`：创建空的管理员表、启用 RLS、撤销普通角色的表访问权限。
- `supabase/schema.sql`：同步包含管理员表结构，供新安装使用。
- `scripts/grant-admin-owner.mjs`：管理员初始化工具，默认只预览；核对项目、用户 UUID、邮箱已验证、账号未删除/停用后才允许显式应用。
- 没有公开的管理员注册、初始化或角色修改接口。

**生产数据库迁移和真实首位 Owner 授权尚未执行。** 在真实账号启用前，应明确确认目标项目和账号，再执行受控初始化。不要把隔离测试账号设为真实 Owner。

## 7. 后续开发前必须保留的上下文

1. **代码基线已变化。** 本轮同步的远端 master 已包含价格、PayPal Live 切换、表单样式和 SEO 等改动。支付代码必须基于当前文件继续开发，不应覆盖成旧版本。
2. **不要沿用旧的支付环境结论。** 早期交接曾记录 Sandbox；今天已同步 Live 切换相关代码，但本轮没有重新核对线上实际支付配置。是否已启用真实收款，要按当前部署单独确认。
3. **后台权限和测试优惠价格是两个概念。** 当前基线包含服务端测试账号价格规则；给账号授予 Owner 不代表自动改变其付款价格。
4. **支付与交付要分开表达。** 后台需要区分已付款、生成中、供应商完成、入库失败、已交付，避免一个 status 混淆业务事实。
5. **历史订单金额不能猜。** 当前仍需设计和补齐报价快照、捕获流水、退款及费用记录，不可用订单数乘当前售价当真实营收。
6. **恢复已有任务和新付费生成要分开。** 原任务查询、补存音频、重新生成必须是不同动作。提交超时或任务号未成功落库时，不得直接自动发起新付费请求。
7. **邮件有两条链路。** 先前已配置的 Supabase Auth SMTP 登录邮件，与应用中的歌曲完成通知不是同一个配置。后台诊断不能仅凭 Worker 是否具备通知邮件配置判断登录邮件不可用。
8. **避免并发重复保存。** 加入管理员同步和定时同步时，现有音频保存的先查后写逻辑需要任务租约与数据库唯一约束配合。
9. **每个任务保留供应商和模型。** 切换默认模型不应改变旧任务查询所用的供应商。
