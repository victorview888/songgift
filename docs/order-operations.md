# 订单处理数据基础

数据基础已实现数据库约束、事务 RPC、服务端封装及后台只读处理记录。
2026-11-06 的 T01/T02 已将客户报价、创建/捕获、生成/查询和音频保存入口接入统一服务，
并补充输入快照、临时结果缓存和音频登记/完成事务。当前接入范围、增量迁移和验证见
[客户入口接入](customer-order-operations.md)。尚无管理员操作按钮、生产迁移或真实服务验收。

以下保留基础阶段的接口设计说明；涉及“尚未切换”与“下一阶段”的段落属于原始阶段记录，
现有入口状态以客户入口接入文档和实际代码为准。

## 迁移与历史数据

按顺序执行（当前仅在内存 PostgreSQL 测试，未执行生产迁移）：

1. `20261105_admin_permissions.sql`
2. `20261105_admin_audio_audit.sql`
3. `20261105_order_operations.sql`

`supabase/schema.sql` 同步包含完整结构，仅用于新安装；现有数据库使用增量迁移。
不要在新版本之后重跑旧的音频审计迁移，它会恢复旧版 action/result 约束。
回滚应用代码时保留已记录事实，不删除这些表、流水或资产。生产迁移须单独安排。

历史订单的报价、币种、支付环境、任务外键均保持 NULL；不使用当前价格或环境回填。
已有音频不搬迁、不去重；新唯一索引仅约束非空 generation_job_id 的最终资产。
缺少可信报价的旧 PayPal 订单需单独核实，报价准备函数拒绝给它们补猜测价格。

## 服务端事务接口

所有 RPC 均为 invoker、固定空 search_path，并撤销 public/anon/authenticated 执行权限。
新表启用 RLS、撤销客户角色访问。客户原有订单/音频策略不变，服务端成员检查仍不可省略。
`src/lib/services/order-operations.ts` 不请求模型、PayPal 或 Storage，仅封装 RPC；
其结果和租约只能留在服务端。后台历史查询使用独立白名单投影，不返回租约/提交令牌。

| RPC | 保证与调用前提 |
| --- | --- |
| prepare_songgift_checkout | 按订单/用户锁行，首次保存 USD 整数美分报价和环境，后续返回原报价；trigger 禁止改写。服务层只采用已验证身份的服务器价格。必须在创建 PayPal 订单之前调用 |
| record_songgift_capture | 调用方先用订单所存环境向 PayPal 读取并核实完整捕获证据；RPC 匹配归属、PayPal 号、环境、币种、金额后，原子写入捕获流水、paid_at 和事件。它自身不向 PayPal 查单，不能用客户端声称“已付款”作为输入 |
| reserve_songgift_generation | 首次预留返回 created=true 和 90 秒租约；重放请求返回 created=false、不返回租约令牌。仅 created=true 可调用生成接口。不同请求不能替换已有任务，遗留 generating/failed/completed 状态也不能绕过 |
| bind_songgift_generation | 原租约未过期才可绑定供应商引用。供应商、环境、模型、提交键和已有外部任务号不可改写；外部任务号跨订单唯一 |
| claim_songgift_job | 为查询/保存已有任务获取新租约。仍在租约内拒绝并发处理；过期 submitting 转为 needs_review，不授予重提权限。没有任务号的未知提交不能恢复为新的生成 |
| settle_songgift_job | 仅当前租约可写回状态。音频保存失败保持 storing；不能把保存失败归为供应商失败后再生成 |
| finish_songgift_generation | 仅匹配订单与任务的最终资产登记后才完成；状态、事件原子提交，重放完成幂等。需先真正上传音频，再登记资产；数据库无法代替 Storage 实际文件验证 |
| begin_songgift_admin_operation | 重新核查有效 Owner、目标和原因代码，先持久化请求与事件。只有 created=true 可继续处理；相同请求键返回已有操作，不重复执行；不同内容复用键拒绝 |
| finish_songgift_admin_operation | 同一操作者幂等记录结果，已结束记录不能改成另一结果。允许记录已经开始操作的结果，即使处理中成员权限已撤销；后续外部操作仍需遵循入口鉴权与租约规则 |

付款流水按支付商、环境、类型、外部流水号去重；第一版每个订单最多一笔完整捕获。
退款表字段仅预留事实记录，尚无退款命令。流水和订单事件对 service_role 也不开放更新/删除。
任务历史允许后续增加尝试，但本阶段不提供“再次付费生成”的预留函数或公开入口。

新音频对象采用 `orderId/jobId/final.ext` 的确定路径。该路径帮助后续实现幂等上传，
**目前原有保存入口尚未切换**，不能宣称已经解决所有旧入口的并发保存问题。

## 后台读取与审计边界

`GET /api/admin/orders/[id]/history` 使用 adminRoute，逐次验证当前资格；
只返回报价和最新各 50 条流水、任务、事件及审计，明确截断标志。
无迁移/数据库故障返回 503，不返回内部错误。详情页面在历史不可用时保留原有只读资料。

扩展审计仅允许核对付款、同步原任务、恢复音频保存三类处理，以及既有音频访问。
使用固定原因/错误代码，不接受任意 JSON、供应商响应或自由文本来承载令牌、故事和签名地址。
开始请求必须先持久化，失败即停止；崩溃可留下 requested，不能据此自动重做外部操作。
完整日志查询页面、用户/概览/系统页面仍待开发。

## 下一步接入顺序

1. 客户 checkout 使用存储报价和稳定 PayPal 请求键；金额展示、创建和捕获均读同一快照。
2. 捕获读取真实 Capture ID/金额/币种/时间，并通过事务保存；旧记录走显式核实流程。
3. 生成提交和状态查询共用上述任务/租约，按每个任务的固定供应商及模型路由。
4. 确定路径上传、资产唯一约束与完成事务共同接入所有保存入口；处理上传成功但登记失败。
5. 在这些入口接入并通过隔离验收后，再实现管理员核对付款、同步任务、恢复保存按钮。

不得用 capture 代替只读查单，不自动重提未知提交，不开放手动“已付款/已完成”修改。

验证包括：实际内存 PostgreSQL 上的增量迁移、重复迁移和新安装 schema；报价冻结、
捕获去重与跨订单拒绝、未知提交不重发、任务引用唯一、租约互斥/失效、匹配资产后完成、
审计请求只执行一次和客户角色隔离。HTTP 与浏览器测试使用模拟支付/任务数据，不连接
真实 PayPal 或音乐服务。poll_count 当前计数为处理租约获取次数，包含保存恢复检查，
不作为成功供应商查询次数或任务成功率指标使用。
